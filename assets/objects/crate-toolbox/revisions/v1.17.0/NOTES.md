- **Checked installed three@0.170.0:** fresh `Material` / `MeshBasicMaterial` constructors do not assign `uniformsGroups` (`uniformsGroups === undefined` and `Object.hasOwn` is false). `ShaderMaterial` assigns `this.uniformsGroups = []`. `ShaderMaterial.copy` assigns `this.uniformsGroups = cloneUniformsGroups(source.uniformsGroups)`, which builds a new array and calls `.clone()` on each group. `RawShaderMaterial` extends `ShaderMaterial`, so it keeps that constructor array. `WebGLPrograms` does not read `uniformsGroups`. `getUniforms` still resolves shaderID from `shaderIDs[material.type]`. MeshBasic stays shaderID `'basic'` and clones `ShaderLib` uniforms.
- **Why:** A leftover own `uniformsGroups` on a color-only MeshBasic (DCC / `ShaderMaterial.copy` bleed) is not consulted by `WebGLPrograms` (shaderID stays `'basic'`; `getUniforms` still clones `ShaderLib`). `WebGLRenderer.setProgram` walks `material.uniformsGroups` and calls `WebGLUniformsGroups.update` / `bind` only when `material.isShaderMaterial || material.isRawShaderMaterial`. MeshBasic is neither, so the leftover array does not invent a custom shader path, does not upload uniform buffer objects, and does not change draws, tris, or attrBytes. The leftover value (an array, `[]`, `{}`, `null`, or an own `undefined`) is still an own property, which is not the r170 MeshBasic absence, and it can retain heap and confuse ingest/debug. Assigning `[]` or `{}` stores an own property. Deleting the own property restores the r170 absence and is load-time packaging. On clean procedural materials `uniformsGroups` is already absent, so draws, tris, and attrBytes stay unchanged vs v1.16.0.
