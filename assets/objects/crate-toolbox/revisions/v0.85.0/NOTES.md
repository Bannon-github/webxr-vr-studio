- **Verified r170 API (three@0.170.0 in this repo; do not assume):** the Mesh constructor calls `this.updateMorphTargets()` (`REVISION` 170). That method assigns `morphTargetInfluences` and `morphTargetDictionary` only when `Object.keys(geometry.morphAttributes).length > 0`. A fresh `new Mesh(geometry, material)` with no morphAttributes leaves both properties absent (`undefined`; `Object.hasOwn` false). `Mesh.copy` copies them when the source defines them (`this.morphTargetInfluences = source.morphTargetInfluences.slice()` and `this.morphTargetDictionary = Object.assign({}, source.morphTargetDictionary)`). GLTFLoader `updateMorphTargets` calls `mesh.updateMorphTargets()` and may write `meshDef.weights` into `morphTargetInfluences`; weight animation tracks select nodes with `if (object.morphTargetInfluences)`. DCC / copy paths can therefore leave a non-empty influence array and/or a dictionary on a node even when this prop’s color-only stand-ins have no morphAttributes (geometry morph attrs are already blocked by `colorOnlyGeometryBlocksPack` / the pack pipeline) and lid / latch / tool / fastener motion is procedural (`tryUse` / `tryDriveFastener`). r170 `WebGLRenderer` calls `WebGLMorphtargets.update` only when `geometry.morphAttributes.position`, `.normal`, or `.color` is defined — so this pulse does not claim a morph-texture upload on these stand-ins. A present array, including empty `[]` (still truthy), looks present to those node checks.
