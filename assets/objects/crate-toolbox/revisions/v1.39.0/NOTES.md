The v0.37–v1.38.0 pipeline stays intact; v1.39.0 adds the bumpMap pin after the isSpriteMaterial pin.
- **Why bumpMap, not size:** `Material.size` cannot be stored by `Material.setValues` on MeshBasic (`this.size === undefined`, so the key is skipped) and `MeshBasicMaterial.copy` does not copy it. `refreshUniformsCommon` does not read `material.size`. `refreshUniformsPoints` does, and that else-if is not taken while `isMeshBasicMaterial` is true, so a delete pin for `size` never changes the MeshBasic refresh path. `emissive` is read earlier in `refreshUniformsCommon`, but `MaterialLoader` only calls `emissive.setHex` when `material.emissive !== undefined`, so a fresh MeshBasic cannot gain an own `emissive` from that loader.
- **Why bumpMap can be own:** installed three@0.170.0 `MeshBasicMaterial.js` does not mention `bumpMap`. A fresh `MeshBasicMaterial` has `bumpMap === undefined` and `Object.hasOwn(material, 'bumpMap') === false`. `setValues` rejects `bumpMap`. `Material.copy` and `MeshBasicMaterial.copy` do not copy it. `Material.toJSON` writes `bumpMap` and `bumpScale` when `bumpMap` is a texture. `MaterialLoader` then assigns `material.bumpMap = getTexture(json.bumpMap)` and `material.bumpScale = json.bumpScale` with no type check, so the JSON round-trip leaves both as own keys on a new `MeshBasicMaterial`.
- **Why the absence:** while `isMeshBasicMaterial` is true, `refreshMaterialUniforms` calls `refreshUniformsCommon`. `if (material.bumpMap)` copies `material.bumpMap` into `uniforms.bumpMap` and writes `uniforms.bumpScale` from `material.bumpScale`. `WebGLPrograms.getParameters` sets `bumpMap: !!material.bumpMap`, which enters the program cache key. `WebGLProgram` emits `#define USE_BUMPMAP` when that parameter is true. shaderID for `MeshBasicMaterial` stays `'basic'`. A leftover own `bumpMap` is not the r170 MeshBasic constructor shape and changes the basic program. `delete material.bumpMap` restores the absence. This pulse does not delete `bumpScale` or `normalMap`.
