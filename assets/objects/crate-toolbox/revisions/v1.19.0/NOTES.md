- **Checked installed three@0.170.0:** fresh `Material` / `MeshBasicMaterial` constructors do not assign `fragmentShader` (`fragmentShader === undefined` and `Object.hasOwn` is false). `Material.js` does not mention `fragmentShader`; `Material.copy` and `MeshBasicMaterial.copy` do not copy it. `ShaderMaterial` assigns `this.fragmentShader = default_fragment`. `ShaderMaterial.copy` assigns `this.fragmentShader = source.fragmentShader` (the source string, not a rewritten stub). `ShaderMaterial.toJSON` writes `data.fragmentShader = this.fragmentShader`. `RawShaderMaterial` extends `ShaderMaterial` and does not assign its own `fragmentShader`, so it keeps that constructor string. `MaterialLoader.parse` assigns `material.fragmentShader = json.fragmentShader` when `json.fragmentShader !== undefined`, including onto a MeshBasic. `WebGLPrograms.getParameters` uses `ShaderLib[shaderID].fragmentShader` when `shaderIDs[material.type]` is set. MeshBasic stays shaderID `'basic'`.
- **Why:** A leftover own `fragmentShader` on a color-only MeshBasic (DCC `MaterialLoader.parse` bleed, or a mistaken `ShaderMaterial.copy`) is not the program string `WebGLPrograms` compiles for MeshBasic. When shaderID is `'basic'`, `fragmentShader` comes from `ShaderLib.basic`, and `getProgramCacheKey` records that shaderID rather than `material.fragmentShader`. `WebGLShaderCache.update` runs only on the custom path (shaderID absent). The leftover string does not invent a custom shader path and does not change draws, tris, or attrBytes. The leftover value (a GLSL string, `''`, `null`, or an own `undefined`) is still an own property, which is not the r170 MeshBasic absence. Assigning `''` or a stub stores an own property. Deleting the own property restores the r170 absence and is load-time packaging. On clean procedural materials `fragmentShader` is already absent, so draws, tris, and attrBytes stay unchanged vs v1.18.0. This pulse does not invent headset milliseconds. 90 Hz ship (~11.1 ms) / 72 Hz fallback are **requested**, not measured.
