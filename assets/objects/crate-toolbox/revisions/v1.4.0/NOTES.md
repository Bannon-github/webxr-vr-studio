- After v1.3.0 pinned leftover Mesh / Object3D `name` to the r170 constructor default empty string (`mesh.name === ''`) on packed color-only unlit MeshBasic visual meshes except reserved names (`lidMesh`, `latchMesh`, `fastenerMesh`, `collider_*`; mesh-name-empty **10**), **`pinColorOnlyUnlitBasicMeshUserData` / `pinColorOnlyVisualMeshUserData` pin leftover Mesh / Object3D `userData` to the r170 constructor default empty plain object (`mesh.userData` is a fresh `{}` with `Object.prototype` and no own keys)** on those same visual meshes (body LOD leaves + lid/latch/tool + fastener; reserved-name visuals are included). Fail-soft packaged paths (no `lod*` groups) still run the visual pin, including the fastener. Assign a fresh `mesh.userData = {}` only when it is not already an empty plain object (missing, non-object, any own string or symbol keys, or a prototype other than `Object.prototype`). Do not share one `{}` across meshes. An already-empty plain object is left as-is, including when two meshes already share that empty object. Two meshes that need a replacement each get their own `{}`. Does **not** replace the mesh, the material, the geometry, the attributes, or the typed arrays. Does **not** touch Mesh / Object3D `name` (v1.3.0 mesh-name-empty stays; reserved names stay). Does **not** touch Material `name` (v1.2.0 material-name-empty stays). - **Checked installed three@0.170.0:** the Object3D constructor assigns `this.userData = {}`. `Mesh` does not override `userData`. `Object3D.toJSON` writes `object.userData` only when `Object.keys(this.userData).length > 0`. `Object3D.copy` assigns `this.userData = JSON.parse(JSON.stringify(source.userData))` (a clone, not a shared reference). `ObjectLoader.parseObject` assigns `object.userData = data.userData` when `data.userData !== undefined`. Stock `GLTFLoader` `loadMesh` calls `assignExtrasToUserData(mesh, meshDef)` after naming the mesh, and `_loadNodeShallow` calls `assignExtrasToUserData(node, nodeDef)`. When the node has one object, that object is the mesh, so node extras land on `mesh.userData`. `assignExtrasToUserData` `Object.assign`s an object `extras` onto `userData`. `WebGLRenderer` does not read `mesh.userData` (no `userData` access). v1.3.0 pinned `mesh.name` and left `mesh.userData` alone, so DCC / glTF extras can still sit on the packed color-only visuals. This pulse pins those leftovers on the visual meshes only.
- **Why:** Stock GLTFLoader and ObjectLoader can leave DCC extras on `mesh.userData`. After the v1.3.0 mesh-name pin, those extras can still sit on static packed color-only MeshBasics. `WebGLRenderer` does not key draws on `mesh.userData`. Clearing leftovers to a fresh `{}` is load-time L3 packaging only: no draw / tri / attrBytes change. Studio metadata stays on the entity/root, the tool Group, and collider meshes so pick / activity / LOD / fastener lookup keeps working. Pre-upload draws / tris / verts / attrBytes on clean procedural meshes are unchanged vs v1.3.0. This pulse does not invent headset milliseconds.
